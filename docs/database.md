# CoopManage Rwanda — Database Design

PostgreSQL 16, accessed exclusively through Prisma ORM.
Status: **Phase 0 baseline.** Tables are created by migration in the phase noted against each group.

---

## 1. Conventions

| Rule | Decision |
| --- | --- |
| Primary keys | `uuid` generated by the database (`gen_random_uuid()`), never sequential integers |
| Human references | Separate readable codes: `COOP-00452`, `SL-2026-000045`, `EX-2026-000112` |
| Money | `numeric(14,2)`, Prisma `Decimal`. Never `float`, never `Int` cents |
| Quantities | `numeric(14,3)` — supports litres, kilograms and fractional units exactly |
| Timestamps | `timestamptz`, `created_at` and `updated_at` on every mutable table |
| Dates without time | `date` for accounting dates such as `occurred_at`, `joined_on`, `paid_on` |
| Tenant column | Every tenant-owned table carries `cooperative_id` with a foreign key and an index |
| Deletion | `RESTRICT` by default. `CASCADE` only for rows that cannot exist alone (sale items, agenda items, role permissions) |
| Soft state | Business records use a `status` enum. Financial and stock rows are voided and reversed, never deleted |
| Enums | PostgreSQL enums via Prisma for closed sets; lookup tables where cooperatives may add values |
| Naming | `snake_case` in the database via `@map`, `camelCase` in Prisma models |

Every unique constraint on tenant-owned data is **composite with `cooperative_id`**. Two
cooperatives may both have a product called "Ibirayi" and a member coded `COOP-00001`.

## 3. Identity and access (Phase 2)

### User
Platform-level identity. A user may serve more than one cooperative.

| Column | Type | Notes |
| --- | --- | --- |
| id | uuid pk | |
| email | citext unique | login identifier |
| password_hash | text | Argon2id |
| full_name | text | |
| phone | text null | staff phone, optional |
| locale | enum(EN, RW) default EN | follows the user across devices |
| is_platform_admin | boolean default false | system administrator flag |
| status | enum(ACTIVE, SUSPENDED) default ACTIVE | |
| must_change_password | boolean default false | set for invited staff |
| last_login_at | timestamptz null | |
| failed_login_count | int default 0 | |
| locked_until | timestamptz null | progressive lockout |
| created_at / updated_at | timestamptz | |

Indexes: unique(email), (status).

### RefreshSession
`id`, `user_id` → User CASCADE, `token_hash` unique, `family_id` uuid, `user_agent`, `ip_address`,
`expires_at`, `revoked_at` null, `replaced_by_id` null, `created_at`.
Rotation: presenting a token whose `replaced_by_id` is already set revokes the entire `family_id`.
Index: (user_id, expires_at).

### PasswordResetToken
`id`, `user_id` CASCADE, `token_hash` unique, `expires_at`, `used_at` null, `created_at`.
Tokens are single use and expire in 60 minutes. The request endpoint responds identically whether or
not the address exists, so it cannot be used to enumerate users.

### Role
`id`, `key` unique (`MANAGER`, `ACCOUNTANT`, `SECRETARY`, `INVENTORY_OFFICER`, `VIEWER`,
`SYSTEM_ADMIN`), `name_en`, `name_rw`, `description_en`, `description_rw`, `is_system` boolean,
`scope` enum(COOPERATIVE, PLATFORM), `created_at`, `updated_at`.
System roles are seeded and cannot be deleted or have their `key` changed.

### Permission
`id`, `key` unique (`finance:create`), `resource`, `action`, `description_en`, `description_rw`,
`scope` enum(COOPERATIVE, PLATFORM). Seeded from a single source of truth in
`packages/shared/src/permissions.ts` so code and database cannot diverge.

### RolePermission
`role_id` + `permission_id` composite primary key, both CASCADE.

### CooperativeStaff
The membership row that makes a user part of a cooperative. **This table is the tenant gate.**

`id`, `cooperative_id` RESTRICT, `user_id` RESTRICT, `role_id` RESTRICT, `job_title` null,
`status` enum(ACTIVE, INACTIVE) default ACTIVE, `invited_by_id` null → User, `invited_at`,
`joined_at` null, `deactivated_at` null, `created_at`, `updated_at`.
Unique (cooperative_id, user_id). Indexes: (user_id, status), (cooperative_id, status).

### StaffPermissionOverride
`id`, `staff_id` CASCADE, `permission_id` RESTRICT, `effect` enum(GRANT, DENY), `granted_by_id`,
`reason`, `created_at`. Unique (staff_id, permission_id).
Effective set = role permissions ∪ GRANT − DENY.

| position | enum(MEMBER, COMMITTEE, SECRETARY, TREASURER, VICE_CHAIR, CHAIRPERSON) default MEMBER | |

Constraints and indexes:
- unique (cooperative_id, member_code)
- unique (cooperative_id, national_id) where national_id is not null
- index (cooperative_id, status), (cooperative_id, last_name, first_name), (cooperative_id, joined_on)
- GIN trigram index on `lower(first_name || ' ' || last_name)` for fast search, plus a trigram index
  on `member_code` and `phone`

Member codes are allocated by incrementing `Cooperative.member_code_sequence` inside the same
transaction that inserts the member, so concurrent registrations cannot collide.

### MemberShare
A ledger, not a balance. `id`, `cooperative_id`, `member_id` RESTRICT,
`type` enum(PURCHASE, TRANSFER_IN, TRANSFER_OUT, REDEMPTION), `quantity` int (positive; direction
comes from `type`), `unit_value` numeric(14,2), `total_value` numeric(14,2),
`issued_on` date, `certificate_no` text null, `finance_transaction_id` null,
`counterparty_member_id` null (transfers), `note`, `created_by_id`, `created_at`,
`voided_at`/`voided_by_id`/`void_reason`.
Current holding = Σ inbound − Σ outbound over non-void rows. Index (cooperative_id, member_id).

### Contribution
`id`, `cooperative_id`, `member_id` RESTRICT,
`type` enum(MEMBERSHIP_FEE, SAVINGS, SHARE_CAPITAL, SPECIAL_LEVY, PENALTY, OTHER),
`amount` numeric(14,2), `paid_on` date, `method` enum(CASH, MOBILE_MONEY, BANK, CHEQUE, OTHER),
`reference` text null, `finance_transaction_id` null → FinanceTransaction,
`note`, `status` enum(POSTED, VOID) default POSTED, `created_by_id`, `created_at`, `updated_at`.
Index (cooperative_id, member_id, paid_on), (cooperative_id, paid_on).

Every posted contribution creates a linked `INCOME` FinanceTransaction in the same database
transaction. The contribution is the member-facing view; the finance transaction is the accounting
view. There is exactly one source of truth for the money.

## 6. Finance (Phase 5)

### FinanceCategory
`id`, `cooperative_id` CASCADE, `kind` enum(INCOME, EXPENSE), `name`, `name_rw` null, `code` null,
`is_system` boolean, `is_active` boolean default true, `created_at`, `updated_at`.
Unique (cooperative_id, kind, name). Seeded with realistic defaults per cooperative type
(Sales of produce, Membership fees, Grants; Transport, Packaging, Salaries, Fuel, Rent, Bank
charges).

### FinanceTransaction
The single money ledger. Balance is always `Σ INCOME − Σ EXPENSE` over `status = POSTED`.

| Column | Type | Notes |
| --- | --- | --- |
| id | uuid pk | |
| cooperative_id | uuid RESTRICT | |
| reference | text | `IN-2026-000123` / `EX-2026-000045`, unique per cooperative |
| kind | enum(INCOME, EXPENSE) | |
| category_id | uuid → FinanceCategory RESTRICT | |
| amount | numeric(14,2) CHECK (amount > 0) | direction lives in `kind`, never in the sign |
| currency | text default 'RWF' | |
| occurred_at | date | the accounting date the user chose |
| method | enum(CASH, MOBILE_MONEY, BANK, CHEQUE, OTHER) | |
| description | text | |
| source_type | enum(MANUAL, SALE, CONTRIBUTION, SHARE_PURCHASE, MEMBER_PAYMENT, STOCK_PURCHASE) | |
| member_id / buyer_id / sale_id | uuid null | optional counterparties |
| document_id | uuid null | attached receipt |
| status | enum(POSTED, VOID) default POSTED | |
| reversal_of_id | uuid null self-reference | a correcting entry points at the original |
| void_reason, voided_by_id, voided_at | | |
| created_by_id | uuid → User RESTRICT | |
| created_at / updated_at | timestamptz | |

Indexes: unique (cooperative_id, reference); (cooperative_id, occurred_at);
(cooperative_id, kind, occurred_at); (cooperative_id, category_id, occurred_at);
(cooperative_id, member_id); (cooperative_id, sale_id).

There is no separate `Income`, `Expense` or `Payment` table. A payment received from a buyer is an
`INCOME` row with `source_type = SALE`; a payment made to a member for delivered produce is an
`EXPENSE` row with `source_type = MEMBER_PAYMENT`. One ledger means one balance, one export and one
place to get the arithmetic right.

Corrections: post a reversal with the opposite `kind`, the same amount and `reversal_of_id` set,
then mark the original `VOID`. Both rows stay visible in the history with a clear label.

## 7. Catalogue, warehouses and inventory (Phase 6)

### UnitOfMeasure
`id`, `cooperative_id` null (null = system-wide seeded unit), `key` (KG, TONNE, LITRE, UNIT, PIECE,
BOX, BAG, SACK, CRATE, BUNCH, HOUR, TRIP), `name_en`, `name_rw`, `symbol`, `precision` int default 2,
`base_unit_id` null, `factor_to_base` numeric(18,6) null, `is_active`.
Unique (cooperative_id, key). Cooperatives may add their own units; nothing in the system assumes
kilograms.

### ProductCategory
`id`, `cooperative_id` CASCADE, `name`, `name_rw` null, `parent_id` null self-reference RESTRICT,
`description`, `is_active`, timestamps. Unique (cooperative_id, name, parent_id).

### Product
`id`, `cooperative_id`, `sku` (unique per cooperative), `name`, `name_rw` null,
`category_id` null RESTRICT, `unit_id` RESTRICT, `type` enum(GOODS, SERVICE),
`track_inventory` boolean default true, `min_stock_level` numeric(14,3) null,
`default_purchase_price` numeric(14,2) null, `default_sale_price` numeric(14,2) null,
`description`, `is_active` boolean default true, `is_demo`, timestamps.
Unique (cooperative_id, sku); index (cooperative_id, is_active), trigram index on name.

### Warehouse
`id`, `cooperative_id`, `name`, `code`, `district` null, `sector` null, `is_default` boolean,
`is_active`, timestamps. Unique (cooperative_id, code). Exactly one default per cooperative,
enforced by a partial unique index on (cooperative_id) where is_default.

### StockLevel
The running balance, maintained only inside transactions that also write an InventoryTransaction.
`id`, `cooperative_id`, `product_id` CASCADE, `warehouse_id` CASCADE,
`quantity` numeric(14,3) default 0 CHECK (quantity >= 0), `updated_at`.
Unique (product_id, warehouse_id). Index (cooperative_id, quantity).

Decrements use a conditional `UPDATE ... WHERE quantity >= :qty`; an affected-row count of zero is
raised as `INSUFFICIENT_STOCK`. This is what prevents two concurrent sales from overselling.

### InventoryTransaction
The immutable movement history. `StockLevel` is a cache of this table and can be rebuilt from it.

| Column | Type | Notes |
| --- | --- | --- |
| id | uuid pk | |
| cooperative_id | uuid | |
| reference | text | `STK-2026-000318`, unique per cooperative |
| type | enum(RECEIPT, ISSUE, ADJUSTMENT, TRANSFER_OUT, TRANSFER_IN, SALE_OUT, SALE_RETURN, OPENING) | |
| direction | enum(IN, OUT) | derived from type, stored for cheap aggregation |
| product_id / warehouse_id | uuid RESTRICT | |
| quantity | numeric(14,3) CHECK (quantity > 0) | always positive |
| unit_id | uuid RESTRICT | unit at time of movement |
| unit_cost / total_cost | numeric(14,2) null | |
| source_member_id | uuid null | produce delivered by a member |
| buyer_id / sale_id | uuid null | |
| counterparty_transaction_id | uuid null | pairs the two halves of a transfer |
| reversal_of_id | uuid null | correcting movement |
| reason | text null | required for ADJUSTMENT |
| occurred_at | timestamptz, `note`, `created_by_id`, `created_at` | |

Indexes: unique (cooperative_id, reference); (cooperative_id, occurred_at);
(product_id, occurred_at); (cooperative_id, source_member_id); (sale_id).

"Products supplied" on a member profile is a sum over `RECEIPT` rows with `source_member_id` set —
no separate deliveries table is needed, and stock and member history can never disagree.

## 8. Buyers and sales (Phase 7)

### Buyer
`id`, `cooperative_id`, `name`, `organization` null, `contact_person` null, `phone` null,
`email` null, `tin` null, `province`/`district`/`sector` null, `address` null, `notes` null,
`is_active`, `is_demo`, timestamps. Unique (cooperative_id, name). Trigram index on name.

### Sale
| Column | Type | Notes |
| --- | --- | --- |
| id | uuid pk | |
| cooperative_id | uuid | |
| reference | text | `SL-2026-000045`, unique per cooperative |
| buyer_id | uuid RESTRICT | |
| warehouse_id | uuid RESTRICT | stock is taken from here |
| sale_date | date | |
| status | enum(DRAFT, CONFIRMED, CANCELLED) default DRAFT | stock moves only on CONFIRMED |
| payment_status | enum(UNPAID, PARTIAL, PAID) | derived from linked income rows |
| subtotal / discount / tax_amount / total | numeric(14,2) | |
| amount_paid | numeric(14,2) default 0 | maintained from FinanceTransaction links |
| currency, note | | |
| confirmed_at, cancelled_at, cancel_reason | | |
| created_by_id | uuid RESTRICT | timestamps |

Indexes: unique (cooperative_id, reference); (cooperative_id, sale_date);
(cooperative_id, buyer_id); (cooperative_id, payment_status).

### SaleItem
`id`, `sale_id` CASCADE, `product_id` RESTRICT, `quantity` numeric(14,3) CHECK (> 0),
`unit_id` RESTRICT, `unit_price` numeric(14,2), `line_total` numeric(14,2), `note`, `position` int.
Index (sale_id).

Confirming a sale is one transaction: validate stock for every line, decrement each `StockLevel`
conditionally, write a `SALE_OUT` InventoryTransaction per line, set the sale to `CONFIRMED`, write
an income FinanceTransaction if payment was taken, and write the audit log. Cancelling a confirmed
sale writes compensating `SALE_RETURN` movements rather than deleting anything.

## 12. Audit, idempotency, reports

### AuditLog (Phase 2, appended to by every later phase)
`id`, `cooperative_id` null (null = platform action), `actor_user_id` null RESTRICT,
`actor_label` text (name and email captured at the time, so the log survives a user rename),
`action` text (`member.created`, `finance.transaction.voided`), `entity_type`, `entity_id` null,
`message_key`, `message_params` jsonb, `before` jsonb null, `after` jsonb null,
`ip_address`, `user_agent`, `request_id`, `created_at`.

Append only. The application has no update or delete path for this table, and the database role used
in production is granted `INSERT` and `SELECT` on it only. `before`/`after` are filtered through the
same redaction list as the logger so password hashes and tokens never land in the audit trail.
Indexes: (cooperative_id, created_at desc), (entity_type, entity_id), (actor_user_id, created_at).

### IdempotencyKey (Phase 13, honoured by Phase 5–7 endpoints from the start)
`id`, `cooperative_id`, `user_id`, `key`, `endpoint`, `request_hash`,
`response_status` int null, `response_body` jsonb null,
`state` enum(IN_PROGRESS, COMPLETED), `created_at`, `expires_at`.
Unique (cooperative_id, key). A replay with a matching hash returns the stored response; a replay
with a different hash is a `409 IDEMPOTENCY_KEY_REUSED`.

### ReportRun (Phase 8)
`id`, `cooperative_id`, `type`, `params` jsonb, `format` enum(PDF, CSV, XLSX),
`status` enum(PENDING, READY, FAILED), `storage_key` null, `error_message` null,
`generated_by_id`, `created_at`, `completed_at`. Lets a finished report raise a notification and be
downloaded again without regenerating it.

### AssistantConversation / AssistantMessage (Phase 14)
Conversation: `id`, `cooperative_id`, `user_id`, `title`, timestamps.
Message: `id`, `conversation_id` CASCADE, `role` enum(USER, ASSISTANT), `content`,
`tool_calls` jsonb null, `data_snapshot` jsonb null, `created_at`.
`data_snapshot` stores the rows the answer was built from, so any figure the assistant states can be
traced back to the query that produced it.

## 13. Seed and demonstration data

`prisma/seed.ts` is idempotent and split into two parts:

1. **Reference data, always applied.** Permissions, system roles, cooperative types, system units.
2. **Demonstration data, only when `SEED_DEMO=true`.** One cooperative — *Umurenge Farmers
   Cooperative* in Musanze — with 120 members bearing realistic Rwandan names, 14 products,
   3 warehouses, 9 buyers, twelve months of income and expenses, inventory movements, sales,
   meetings with attendance and decisions, documents and audit history.

Every demonstration row carries `is_demo = true` and the cooperative name is suffixed in the
interface with a "Demonstration data" badge, so nobody mistakes it for live records. A
`npm run db:demo:purge` script removes every `is_demo` row in dependency order.

## 14. Migration and backup policy

- Schema changes only ever ship as Prisma migrations. Nothing is altered by hand in any environment.
- Migrations are additive first: add a nullable column, backfill, then add the constraint. A
  destructive migration must be accompanied by a written rollback note in the pull request.
- `prisma migrate deploy` runs in the release pipeline before the new backend starts.
- Backups: Supabase daily automated backups with 7-day retention on production, plus a documented
  `pg_dump` script in `scripts/backup-db.mjs` for on-demand snapshots. The restore procedure is
  written down in `docs/deployment.md` and is verified once per release. No claim that backups exist
  will be made in the product interface until this is actually configured.
